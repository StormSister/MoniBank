# MBGATE gateway

`MBGW` and `MBGATE` form the single online entry point used by the Java terminal workers. `MBGW` is the four-character KICKS transaction entered on the terminal; `MBGATE` is the COBOL program registered for that transaction.

## Input from the terminal

The BMS map accepts this protocol envelope:

| Field | Width | Meaning |
|---|---:|---|
| Operation | 8 | Logical operation such as `GETCUST` or `ADDCUST` |
| Request ID | 8 | Correlation ID generated by Java |
| Input length | 4 | Decimal length, for example `0105` |
| Input | 512 | Operation-specific fixed-width payload |

The input area is split across eight 64-character screen fields. `MBGATE` collects them, changes BMS low values to spaces and rejects a missing operation, an invalid request ID, a non-numeric length or input longer than 512 characters.

## Common COMMAREA

After screen validation, `MBGATE` fills the 855-byte [`MBGWCA`](https://github.com/StormSister/MoniBank/blob/main/monibank-backend/src/main/resources/jcl/application/build/kicks/PUTGWCA.jcl):

| Part | Size | Purpose |
|---|---:|---|
| Protocol version | 2 | currently `01` |
| Request ID | 8 | result correlation |
| Operation | 8 | routing and response validation |
| Input length | 4 | meaningful input bytes |
| Input | 512 | business-program payload |
| Data count | 1 | zero or one preview record on the terminal |
| Data record | 160 | optional `MBR;D` preview |
| Header record | 160 | final `MBR;S` or `MBR;E` preview |

The map is only a transport envelope. Every target program owns and validates the layout of its business input.

## Routing

[`MBGATE.cob`](https://github.com/StormSister/MoniBank/blob/main/monibank-backend/src/main/resources/cobol/application/gateway/MBGATE.cob) selects an explicitly allowed program and calls it with `EXEC CICS LINK`. The current routes are:

| Area | Operations |
|---|---|
| Customers | `GETCUST`, `ADDCUST` → `ADDCUSG`, `LISTCUST`, `CHGCUST` |
| Accounts | `LISTACCT`, `ADDACCT`, `CHGACCT` |
| Cards | `LISTCARD`, `ADDCARD`, `CHGCARD` |
| Transactions | `POSTTXN`, `LISTTXN` |
| Daily processing | `POSTINT`, `DAYSTAT`, `GETSTAT` |

An unknown operation is not dynamically executed. It remains outside this allow-list and produces an error screen.

## Response checks and replay protection

After the linked program returns, the gateway requires:

- prefix `MBR`;
- the same request ID and operation;
- a final type of `S` or `E`;
- at most one valid `D` preview record in the COMMAREA.

Complete list results are transported by `MBRESULT`, not squeezed into the one-record terminal preview.

Before performing the `LINK`, `MBGATE` changes its one-byte return marker from `Y` to `R`. If the same result screen is submitted again, it starts a new request instead of executing the previous write twice. An invalid response is shown with the explicit warning `DO NOT RETRY WRITES`.

## Terminal lifecycle

On first entry, `MBGATE` displays `READY`. After execution it displays `SUCCESS` or `ERROR`, the correlated request ID and a preview of the returned records. Enter prepares a new request; Clear exits the transaction.

Java treats the expected `MBGW` map as the worker's ready state. STEVE or SOFIA fills the fields and waits for the correlated acknowledgement before the session becomes available to the shared queue again.
